# 业务归属与权限决策

> 本文件中的“待确认”必须在对应对象编码前完成。不要在开发过程中临时猜测归属规则。

## 1. 决策原则

直接保存范围快照的典型条件：

- 对象可以独立高频查询；
- 上游关联可能变化或删除；
- 历史追溯必须稳定；
- 推送、日志或后台任务需要无需复杂联表即可过滤。

通过关联校验的典型条件：

- 关联稳定且唯一；
- 查询频率不高；
- 历史追溯可以接受联表；
- 不会因为关联删除而失去归属。

## 2. 从属对象决策矩阵

| 对象 | 当前归属基础 | 初步方案 | 状态 |

| PrintJob | taskNo + factory | 保留 factory；deliveryArea 快照待论证 | 待确认 |

## 3. 计划类对象

### WeeklyPlan

当前批次已经有 `factory`。

必须明确：

- 查询是否按 factory/area 过滤；
- 导入时普通账号是否强制为自身工厂；
- 管理员从文件解析 factory 时是否校验合法值；
- 激活批次是否要求当前账号有权操作该工厂；
- 同工厂是否允许多个活动批次；
- 区域是否是周计划的必要维度。

### SimpleBOM

当前 `SimpleBomBatchEntity` 没有 factory。

建议：如果不同工厂可以维护不同 BOM/活动批次，则增加 `factory`，并至少做到：

```text
active batch = per factory
```

如果 BOM 确认全公司唯一，应由业务方明确签字，不因技术方便默认全局。

### ProductionPlan / MaterialDemand / PurchaseRequirement

当前均没有 factory。

建议业务链：

```text
ProductionPlan
      ↓ 继承/固化范围
MaterialDemand
      ↓ 继承/固化范围
PurchaseRequirement
```

需要确认是否只按工厂隔离，还是还需要 deliveryArea。

## 4. Inventory

当前只有 warehouseCode/locationCode/materialCode，没有范围字段。

建议直接增加：

```text
factory
delivery_area
```

理由：

- Inventory 是独立高频查询对象；
- Dashboard 直接统计 Inventory；
- 只依赖 warehouseCode 反查 Mapping 会受 Mapping 变化/删除影响；
- 历史库存归属需要稳定。

待确认：库存唯一键是否需要加入 factory/deliveryArea。

## 5. Box

当前 `areaCode` 不能直接等同于 DataScope 的 `deliveryArea`，必须先确认业务语义。

编码前确认：

1. 一个 Box 是否可以跨任务重复使用？
2. 换箱后 Box 归属是否变化？
3. Box 属于“创建它的区域”“当前所在区域”还是“最后一次任务区域”？
4. `areaCode` 是否就是配送区域，还是箱池/物理区域编码？

初步建议：Box 跨任务存在时，应有自身稳定的 factory 归属，不应永远通过“最后任务”推断。

## 6. Label

当前有 areaCode，但没有 factory。

需要验证：

- warehouseCode 是否唯一命中 Mapping；
- Mapping 删除/停用后是否仍要求 Label 可追溯；
- Label 是否有独立列表、导出、历史查询。

如果需要独立追溯，建议保存工厂快照；deliveryArea 是否快照按查询频率和业务变化规则确认。

## 7. AGV Job

当前主要通过 taskNo 关联 Task。

第一阶段推荐：

- 派单前通过 Task 校验范围；
- 回调通过可信 job/task 标识反查 Task；
- Agent/AGV 机器身份绑定允许工厂；
- 禁止回调请求体自行决定 factory。

如果后续 AGV 列表、统计、告警高频，再增加 factory/deliveryArea 快照。

## 8. PrintJob

已保存 factory。

待确认是否增加 deliveryArea。判断依据：

- taskNo 关联覆盖率和稳定性；
- PrintJob 是否高频按区域独立查询；
- Task 删除/归档后是否仍要求 PrintJob 独立追溯；
- 打印代理是否只按 factory 领取，还是未来还按区域划分 Agent。

## 9. MenuPermission

推荐决策：

```text
Role             功能基线
MenuPermission   仅收窄菜单/入口可见性
DataScope        数据范围
```

如果 MenuPermission 可以针对同一 Role 的不同账号细化功能，必须规定：

```text
最终功能权限 = Role ∩ MenuPermission
```

它仍不能扩大 DataScope。

不建议根据“账号有某工厂范围”动态生成不同工厂菜单项来作为安全边界；数据筛选和权限仍应由后端 DataScope 完成。

## 10. 外部系统身份决策

### Print Agent

推荐目标方案：建立 `sys_print_agent`：

```text
agent_id
credential_hash
factory
enabled
last_seen_at
```

认证：

```text
X-Agent-Id + X-Agent-Credential
```

领取和回调必须反查 Agent factory。

### 第一阶段过渡方案

如果暂时不拆统一 API Key：

- 必须明确 `SYSTEM` 仅代表“机器身份已认证”，不代表全局业务授权；
- PrintJobService、AgvService 等业务层仍需基于可信业务对象校验 factory；
- 过渡方案必须有后续替换计划。

### SAP / IMS / PPC

应分别确认：

- 独立凭据；
- 系统标识；
- 允许工厂；
- 请求幂等键；
- 回调/读取业务范围；
- 凭据轮换和审计。
