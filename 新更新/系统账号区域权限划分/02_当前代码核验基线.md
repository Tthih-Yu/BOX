## 1. 总体结论

当前系统已经具备：

- 7 个 Role 功能权限；
- Mapping、Task、PrintJob 等部分业务范围字段；
- 前端工厂/区域筛选界面；
- 部分扫码归属传递；
- 基础 `(factory, created_at)` 索引。

尚未形成账号级 DataScope 安全边界。准确表述为：

> 在角色权限和业务状态允许的情况下，普通账号仍可能读取或操作其他工厂、其他配送区域的数据。

## 3. 账号、认证、Session、上下文

当前：

- `UserEntity` 没有 `factory`。
- 没有用户—配送区域关联表/实体/Repository。
- 用户 DTO 没有 `factory`、`deliveryAreas`。
- `Users.vue` 不能为账号分配工厂和多个配送区域。
- `LoginResult` 没有范围字段。
- `SessionUser` 没有范围字段。
- WebSocket Ticket 复用同一 SessionUser，因此没有范围字段。
- `AuthTokenFilter` 只绑定用户和 Role。
- `RequestContext` 只有用户和 Role。
- 没有统一 `DataScopeService`、`canAccess()`、`requireAccess()`。

## 4. Task

- Repository 的列表、日期、状态、统计、待打印和 taskNo 查询没有统一 factory/area 条件。
- `TaskService.list()` 仍存在全局 Top1000 查询。
- 按 taskNo 加锁后执行取消、接单、拣料、配送、收货、异常、重试等操作时，主要校验 Role 和状态，没有统一校验实体 DataScope。
- 扫码创建 Task 已能从 Mapping 传递 factory，但归属解析仍存在默认值和多候选问题。

## 5. Mapping

当前高风险点：

- `deleteByDeliveryArea` 只按区域删除，未同时限定工厂。
- `scope=ALL`、区域删除、IDs 删除、全量导出、导入覆盖/upsert 没有账号 DataScope。
- 普通账号保存时后端没有强制覆盖为当前账号范围。
- 部分逻辑会把缺失配送区域默认成 `1`。
- 全局 upsert 时没有把工厂和区域统一纳入权限和业务唯一性判断。

## 6. PrintJob

- `PrintJobEntity` 已有 `factory`，没有 `deliveryArea` 快照。
- 列表、编号查询、状态查询、待领取查询没有统一范围条件。
- 无筛选时存在全局分页查询。
- 从 Task 创建时可以继承工厂，但人工入口需要先校验 Task 范围。
- Print Agent 当前仍使用统一外部 API Key + `SYSTEM` 身份，未绑定独立 Agent 和工厂。

## 9. Dashboard、统计、日志和维护

已确认存在全局查询形态：

- `DashboardService.dashboard()` 使用 Inventory `findAll()` 后在内存统计。
- Material、Box、Label 存在全表 count。
- Task 存在全量读取再 stream 过滤。
- ScanLog 最新记录缺少范围条件。
- 物料用量统计读取范围内外全部 Task/Mapping 后再处理的风险。
- 日志接口和导出存在全局 Task、Print、Interface、Scan 日志旁路。
- Recovery、DataQuality 等维护服务遍历全局 Inventory、Box、Label、Task。

Dashboard 是默认首页，属于高风险旁路，应在业务封堵阶段提前改造，并优先于 WebSocket。

## 10. 外部系统认证

当前 `AuthTokenFilter` 对外部系统使用统一 `EXTERNAL_API_KEY`：

```text
X-Api-Key == configuredApiKey
        ↓
userId = 0
username = EXTERNAL_SYSTEM
role = SYSTEM
```

Print Agent、AGV、SAP、IMS、PPC 因此无法天然区分身份、绑定工厂或限制跨工厂业务访问。

## 11. WebSocket 再次核验

该项不是 2026-08-28 的新发现，而是对原指导书结论再次确认：

- `WebSocketConfig` 开放公共 `/topic` Broker。
- `RealtimePushService` 仅传递 `topic + body`，事件无范围元数据。
- 前端订阅公共 `/topic/{topic}`。
- 没有 STOMP `SUBSCRIBE` 范围拦截器。
- 没有可信 Principal 范围。
- 没有用户队列隔离。
- Redis relay 没有按连接权限过滤。

只改 HTTP 不改 WebSocket，仍存在实时数据旁路。

## 12. 导入服务

当前需要重点改造：

- `SimpleBomService`：CSV 流式导入，500 万行量级；缺少工厂信息时激活可能全局生效。
- `WeeklyPlanService`：已有 factory 字段，但导入/激活必须校验账号范围。
- `ImportService`：Mapping 等基础数据导入需要强制范围。

导入不能依赖前端传参作为权限依据。
