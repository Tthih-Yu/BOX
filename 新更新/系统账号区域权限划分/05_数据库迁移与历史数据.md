# 数据库迁移与历史数据

> 职责：只管理 Schema、Migration、索引、历史候选、回填和数据库级恢复。  
> 对象范围类型和字段语义只从 `03` 读取；整体实施顺序只看 `04`；发布验收只看 `06`。

## 1. 数据库原则

- MySQL 和 H2 分开维护兼容 Migration。
- Schema、索引、历史数据候选/回填分离。
- 生产不依赖 `ddl-auto=update`。
- 不覆盖已经执行的 Migration 版本。
- 新增范围列在 Expand 阶段优先可空并向后兼容。
- 未经过历史质量验证前不直接加 NOT NULL。
- 历史归属只生成候选，不用区域名称、默认值或第一条 Mapping 猜测。
- 任何生产写操作前创建并验证当次新备份。

## 2. 已知基础

基线仓库已存在：

```text
V0.9.1__mapping_factory.sql
V0.9.2__task_print_factory.sql
idx_task_factory_created(factory, created_at)
idx_print_factory_created(factory, created_at)
```

实施前必须核验实际 MySQL `INFORMATION_SCHEMA`（或等价结构）；实体字段不能证明生产库已执行 Migration。

## 3. Expand Schema

基础账号结构：

```text
sys_user.factory
sys_user_delivery_area(user_id, delivery_area)
UNIQUE(user_id, delivery_area)
```

`sys_factory`、`sys_delivery_area` 及各业务对象范围字段，只按 `03` 当前已批准/已确认内容生成正式 DDL。

Expand 阶段禁止：
- 直接执行历史全表 UPDATE；
- 未验证数据质量就加 NOT NULL；
- 把未决范围类型写死进 DDL；
- 通过修改旧 Migration 伪造升级历史。

## 4. 字典数据

按 `03` 已确认结构准备：
- factory_code / factory_name；
- area_code / area_name；
- factory 与 area 归属；
- enabled / display_order；
- 必要的历史别名/规范化映射。

数据处理：
- 去除前后空格；
- 比较使用统一大小写规范；
- 停用值禁止新业务使用；
- 历史原值原则上保留，必要时用映射解释，不静默改写。

真实初始工厂、区域和现有账号映射在执行前从 `03` 与实际数据库共同核验。

## 5. 索引策略

不为所有表复制同一个 DataScope 索引。索引必须根据最终 SQL、数据分布和 `EXPLAIN` 设计。

Task 候选方向示例：

```text
(factory, delivery_area, created_at)
(factory, delivery_area, status, created_at)
(factory, delivery_area, print_generated, status)
```

索引评估至少考虑：等值列、area IN 集合、status 选择性、ORDER BY、数据基数、查询频率、写入成本。

SimpleBOM 等大批量导入表需单独评估索引维护成本。

## 6. 历史数据基线

2026-08-26 快照：

```text
Task factory IS NULL      848
PrintJob factory IS NULL  845
```

当时只读分析：
- 848 条缺 factory Task 可按 warehouse_code 命中唯一工厂候选，但仍需核对启用状态、物料号、配送区域和地址；
- 845 条缺 factory PrintJob 中，843 条关联缺 factory Task，2 条未找到 Task。

以上不是生产更新数量；实施前必须重新统计。

## 7. 历史候选与审批流程

1. 重新统计 NULL、空串、非法 factory/area 和分布。
2. 先为 Task 生成候选，不 UPDATE。
3. 验证关联唯一性和关键业务字段。
4. 多候选、无候选、只能凭区域猜测的记录进入人工清单。
5. 业务审批 Task 候选。
6. Task 确认后再生成 PrintJob 候选。
7. 从属对象按 `03` 已批准的权威来源生成候选。
8. 每条候选保存原值、新值、依据、审批人、批次号。
9. 在与生产同版本的验证环境演练。
10. 生产按批准批次执行并逐批校验。
11. 未确认记录保持未归属，仅 ADMIN 可见。

明确禁止：

```text
delivery_area = 1  => 猜归属
LP                 => 猜归属
Mapping 第一条     => 猜归属
直接全表 UPDATE
```

## 8. 导入与范围的数据库约束

普通账号：后端使用可信 factory；area 必须属于允许集合；文件不能扩大授权。

ADMIN：必须明确目标范围或从文件解析并校验合法范围；激活/覆盖前再次验证；冲突检测和唯一键只在批准的业务范围内计算。

数据库唯一约束是否包含范围维度，以 `03` 业务唯一键决策和真实冲突数据为依据，不能仅因“做 DataScope”机械加列。

## 9. Contract 阶段

仅在安全切换完成、数据质量稳定且独立评审通过后考虑：
- NOT NULL；
- 更严格 CHECK/UNIQUE/FK；
- 清理废弃字段或兼容逻辑。

Contract 不是 Expand 的顺手清理项，必须独立评审和演练。

## 10. 数据库恢复

必须分别准备：
- Schema 保留/回退策略；
- 历史回填反向恢复脚本；
- 数据校验 SQL；
- 批次级原值记录和备份位置。

原则：
- 向后兼容 Expand Schema 出现应用问题时通常优先回滚应用并保留新 Schema；是否删除列/表必须以验证环境演练为准。
- 历史回填异常立即停止后续批次，按原值/备份恢复已执行批次。
- 不在正式方案中固化未经演练的 DROP/ALTER 回滚语句。
